## Implementación backend integrada (etapa 1)

- **D1:** el snapshot de client oculta cotizaciones cuyo estado persistido es `Pendiente`, incluso si ya vencieron; manager/admin siguen viendo sus cotizaciones.
- **D2:** al crear una cotización con solicitud anónima, la vinculación al cliente elegido y el cambio a `Cotizada` ocurren en la misma transacción; solicitudes de otro cliente se rechazan.
- **D3:** envío de cotización y avisos de cambios de fecha/estado confirman la transición de negocio, pero registran `Pendiente de reintento` cuando el email está vacío.
- **D4:** el reintento relee el contacto actual; sin destinatario devuelve 409 sin mutar el aviso y, con contacto, actualiza la misma fila.
- **D5:** planificar permite encolar en máquina ocupada si es compatible; iniciar conserva el rechazo `MACHINE_BUSY`. Se ajustó la expectativa de la prueba de planificación existente.
- **D7:** `belowMinimum` compara stock físico contra mínimo y se devuelve a manager/admin/operator.
- **D8:** `delayed` compara fecha UTC y estado activo para staff/operator y no se expone al client.

## Verificaciones transversales y alcance de la evidencia

- Mutaciones sin `X-Jacsa-Request` o con origen externo se rechazan; Content-Type incorrecto da 400 `JSON_REQUIRED`, JSON mal formado 400 `INVALID_JSON` y cuerpo superior a 64 KiB 400 `REQUEST_TOO_LARGE`.
- `/api/no-existe` produce 404 `NOT_FOUND`; una ruta no API conserva fallback HTML. Los errores de las pruebas mantienen formato JSON `{error, code}` cuando son respuestas API.
- Los límites ensayados incluyen cantidad/unidades, markup/vigencia, gramos de recepción, precio, memo, campos principales de solicitud, tamaño del cuerpo y fechas. Son casos de frontera representativos, no una prueba combinatoria exhaustiva de cada campo y valor.
- La matriz parametrizada recorre todos los roles no permitidos y sin sesión para E09–E22; E08 sin sesión ya se cubría aparte. Los IDs deliberadamente inexistentes en las llamadas con rol permitido producen 404 de negocio (`*_NOT_FOUND`): eso verifica solo que pasó la autorización y alcanzó el handler, **no** equivale a un flujo feliz. E07 conserva su carácter público; las sesiones de equipo ejercitadas crean solicitudes sin vínculo y no reciben acceso a datos comerciales por ello.
- Este registro no es prueba de UI ni E2E visual: no se abrió navegador. Tampoco es auditoría, certificación ni afirmación de conformidad normativa o de seguridad; describe solo respuestas y comportamiento observados en esta API y en sus fixtures locales.

## Residual de inventario — E07

El inventario de endpoints describe E07 como público/client, mientras la implementación pública no aplica un filtro a sesiones de manager/admin/operator/technology. Se documenta que también pueden crear una solicitud sin vínculo (`client_id=NULL`), incluso si el email/CUIT coinciden con un cliente. Esta observación no amplía permisos comerciales ni atribuye una nueva regla funcional; no se modificó el servidor.

## Estrategia de commit integrada

El cambio integrado de etapa 1 + QA debe ir en **un commit cohesivo `fix(api)`** que agrupe `prototipo/server/app.mjs`, `prototipo/tests/backend.test.mjs` y `documentacion/qa-backend.md`, tras pasar `npm test` y build. Después del commit, el hash del conjunto se recupera con:

```sh
git log -1 --format=%H -- documentacion/qa-backend.md
```

No se incluye el hash dentro del propio informe para evitar autorreferencia; el commit local se crea después de esta revisión y se comunica a coordinación. No se tocaron UI, E2E, configuración ni archivos de dependencias. Los procesos de prueba terminaron y todos los servidores/handles SQLite de los fixtures se cerraron; no se dejó un servidor persistente. Rollback: revertir el commit cohesivo restaura el comportamiento previo, sin migración de esquema ni modificación de datos locales.
